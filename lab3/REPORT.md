# Лаба 3: CI/CD 
Вначале была выполнена базовая часть работы. Как ни странно, я решил сначала сделать [хороший пайплайн](/.github/workflows/good-ci-cd.yml), следуя рекомендациям из текста задания.
Помимо этого были также реализованы [юнит-тесты для бэкенда](/backend/tests), где тестируются ручки с замоканным подключением к базе данных

Сам пайплайн выглядит примерно следующим образом:
1. Установка python вместе с зависимостями, Линт (ruff), запуск unit-тестов (pytest)
2. Сборка docker-образов бэкенда и фронтенда, их сканирование через Trivy (ловит нарушения уровня CRITICAL) и пуш в GitHub Container Repository (GHCR) для сохранения образов
3. Запуск и проверка работоспособности приложения прямо внутри Github Actions (ибо у меня нет личного сервера)

Завести все это дело удалось далеко не сразу (это можно понять по истории запусков пайплайнов). Все это из-за всяческих опечаток, например, в названии машины, на которой запускается джоба, в SHA, в пути к докерфайлам, в общем в таких вещах, которые до запуска особо не проверишь. Главное, что в один момент все заработало :)

В итоге были реализованы следующие так называемые good practices:
1. Версии экшенов зафиксированы по SHA коммита, что защищает от "атаки на цепочку поставок" (Supply Chain Attacks) при использовании тегов версий, в результате чего может быть выполнен вредоносный код
2. Секреты записаны не в открытом виде в коде пайплайна, а в GitHub Actions Secrets
3. Реализовано кеширование зависимостей (pip) и слоев для backend-образа (для frontend-образа кеширование использовать небезопасно из-за того, что в одном из слоев происходит обновление пакетов, а если его закешировать, то есть возможность не подтянуть необходимые патчи безопасности зависимостей)

После этого был реализован [плохой пайплайн](/.github/workflows/bad-ci-cd.yml). Что в нём плохого?
1. Прежде всего, секреты захардкожены
2. Используются плавающие теги для доступа к экшенам вместо зафиксированных версий, не указаны версии устанавливаемых python-пакетов
3. Нет кеширования зависимостей и образов
4. Выполнение пайплайна не останавливается при падении тестов или линта (ошибки просто выводятся в лог запуска)
5. Trivy также не падает при наличии уязвимостей
6. При пуше образы сохраняются только с тегом latest, нет сохранения версий по хешу коммита, из-за чего не будет сохраняться история версий образов

## Звездочка
Для выполнения задания хороший пайплайн был слегка переделан. Стоит сказать, что в версии до добавления отката уже было реализовано сохранение образов не только по тегу latest, но и по хешу коммита, что уже позволяет откатиться к нужной версии в случае чего, поэтому я решил добавить новую джобу auto-rollback для автоматического отката к стабильной версии

Логика нового пайплайна выглядит следующим образом:
1. До джобы run-and-verify все так же, как в предыдущей версии пайплайна
2. В джобе run-and-verify перед деплоем выполняется запоминание предыдущей версии из файла .deploy/current_release.txt, чтобы при падении curl можно было к ней обратиться в auto-rollback
3. Выполняется запуск приложения
4. Если ошибок нет, то хеш коммита новой рабочей версии сохраняется в файл .deploy/current_release.txt, auto-rollback игнорируется
5. Если ошибки есть, то происходит выполнение auto-rollback: находится целевой тег отката, выполняются такие же действия для деплоя, что и в предыдущей джобе, потом выполняется деплой рабочей версии с замером и выводом потраченного времени
6. Происходит проверка работоспособности приложения после отката
7. В файл .deploy/current_release.txt записывается текущая версия как последняя рабочая
